## 1. 요약

| 항목 | 결과 |
| --- | --- |
| 탐지 범위 | 룰 파일 16개(활성 11) · 탐지 유형 16종 → **룰 파일 34개(01\~35, 11은 08에 통합) · 탐지 유형 48종 모두 활성**. 킬체인 7단계(정찰, 초기 침투, 자격증명 접근, 확산, C2, 유출, 영향) 전체에 탐지가 있고 ATT&CK 기법 37개 대응 |
| 기존 룰 정비 | 검토에서 찾은 Critical 3건·High 6건을 모두 수정. 비활성 룰 5개(03·04·05·08·11)는 판정 로직을 새로 써서 4개로 재활성화(11은 08에 통합) |
| 신규 룰 | 1차(PR #12\~#18) 8개, 2차(#63\~#78) 10개. 2차는 식별 안 된 프로토콜, SSH·FTP 무차별 대입, Heartbleed, XSS, 웹 로그인 무차별 대입, **TLS 비커닝**(11-11 판의 가장 큰 공백), 대상 1대 원격 실행, 남의 머신 계정 사용, AI 관련 위협 3종, AD 공격 4종 |
| 공통 인프라 | 근거·탐지 요약(15분 안 반복은 같은 사건으로 묶음)·킬체인 상관(개별 전이 23개 + 묶음 전이 23개)·예외 엔진(예외 파일, drop·suppress, 재시작 없이 반영)·인증 맥락(확산 근거에 계정) |
| 회귀 테스트 | btest 115개(룰·계약·예외·선별 전송 79개, 클러스터 7개, 자산 식별 29개), 합성 pcap 56개. Zeek 9.0.1 전부 통과, 8.0.9는 9.x 분석기가 필요한 5개를 빼고 통과 |
| 공개 데이터셋 검증 | CIC-IDS2017 5일: 공격 14종 중 9종 탐지(범위 안 공격 전부). 놓친 5종은 DoS 4종·DDoS로 탐지 범위 밖. 공격과 무관한 탐지는 튜닝으로 5일 271건 → 19건(하루 평균 약 4건) |
| 고객 운영 트래픽 | 고객 운영 pcap에서 정상 서비스 오탐(보안 제품 통신, QUIC, 푸시·시간 동기화 TLS 포트, 프록시 CONNECT 터널, Windows 배달 최적화)을 찾아 룰 기본값과 예외 초안에 반영. **1시간 이상·DC 포함 구간의 오탐률은 아직 재지 않음** |

**결론:** 검토 결함을 모두 고치고 7단계 전체에 탐지를 갖췄다. 11-11 판의 공백이던 HTTPS 주기 C2(TLS 비커닝)도 채웠다. 공개 데이터셋에서 범위 안 공격을 모두 잡았고, 오탐은 예외 파일 16행과 룰 기본값 조정으로 하루 4건 수준까지 줄였다. 남은 것은 **고객 운영 구간의 장시간 측정으로 오탐률을 확인하는 일**과 운영 편의(비콘 위험도 등급, 심각도 구분)다.

## 2. 목적과 범위

출발점은 기존 nsm_rules(룰 파일 16개 중 11개 활성)였다. 검토(2026-11-09)에서 다음 목적을 세웠다.

1. 현재 룰의 동작 정확성과 운영 위험 점검·수정
2. 비활성 룰 재활성화
3. NSM 관점에서 비어 있는 공격 단계의 탐지 추가
4. 자산 식별 PoC 머지와 OCSF 변환기 연동을 위한 기반 정리
5. 운영 Zeek 9.x 기준 확정(CI는 9.0.1·8.0.9)

| 구분 | PoC 범위 | 범위 밖 |
| --- | --- | --- |
| 센서 | 탐지 룰, 공통 인프라(근거·탐지 요약·ATT&CK 매핑·억제·상관·예외 엔진·로그 필터), 설정, 회귀 테스트, CI | 패킷 캡처·센서 배포 |
| 검증 도구 | pcap 통합 실행(`tests/run_pcap.sh`)과 통합 리포트(`<pcap 이름>_report.html`) | Manager 화면 |
| 연동 | 출력 로그 형식 정의(SRS 6장, 목록 필드는 JSON 배열), 자산 식별 센서 머지(#47) | OCSF 변환기 매핑, Manager 연동(다음 단계) |
| 탐지 대상 | 침투 후 활동(정찰·자격증명·확산·C2·유출·영향)과 내부 서버 대상 초기 침투 | 가용성 공격(DoS·DDoS), 파일 악성 판정 |

### 3.2 탐지 범위 변화

| 킬체인 단계 | 정비 전(활성) | 현재 | 추가·변경 |
| --- | --- | --- | --- |
| 정찰 | 포트 스캔, 호스트 스캔 | + AD 정보 수집. 포트 스캔에 SYN 없는 TCP 탐침·UDP 탐침 | 신규 1 |

| 자격증명 접근 | 없음(05 비활성) | NTLM 스프레이, Kerberos 스프레이·무차별 대입, SSH·FTP·웹 로그인 무차별 대입, Kerberoasting, AS-REP Roasting, 외부 NTLM 인증, 이름 해석 포이즈닝, 남의 머신 계정 사용, DCSync, 강제 인증, 원격 레지스트리 하이브 저장, Zerologon | 재작성 1 + 신규 14 |

| C2 | HTTP 비커닝, 암호화 C2, DGA | + DNS 터널링, TLS 비커닝, 비표준 포트 프로토콜, 장기 외부 연결, 식별 안 된 프로토콜, 서버의 AI API 접속 | 재작성 1 + 신규 5 |

### 3.3 공통 인프라

| 구성 | 결과 |
| --- | --- |
| 알람 억제 | 룰마다 정한 억제 기간이 다시 동작(이전에는 공통 묶기 모듈이 모두 0으로 덮어씀). 억제 중인 반복 탐지는 근거도 남기지 않음 |

| 근거(`evidence.log`) | 모든 탐지가 `evidence_id`로 근거와 이어지고, 근거를 notice보다 먼저 기록. 확산·자격증명 탐지는 같은 연결의 NTLM·Kerberos 인증에서 계정과 대표 uid를 채움. 비밀번호 값은 어디에도 남기지 않음 |

| 로그 필터 | 남길 로그·경로를 설정으로 분리, reporter 로그 유지(스크립트 오류 확인 가능) |
| 킬체인 상관 | 클러스터에서 매니저 한 곳에서 판정. 개별 전이 23개 + 단계 묶음 전이 23개(묶음 8개: 정찰·초기 침투·C2·자격증명·도메인 장악·확산·유출·영향). 초기 침투·확산 대상이 다음 단계 출발지가 되는 전이로, 웹서버 침투부터 랜섬웨어까지 한 체인으로 이어짐. 체인이 피해 host별로 갈라져도 갈래마다 탐지 1건 |
| 출력 형식 | JSON 한 줄 한 행. 목록 필드(`techniques`, `killchain_stages`, `victims`, `evidence_ids`, 예외 `scope`)는 JSON 배열 |
| 클러스터 | 07 비커닝 상태를 (출발지, 목적지)별로 한 노드에 모음. SumStats 룰은 매니저 집계. 예외 파일은 매니저가 읽어 워커에 배포, 인증 맥락은 워커가 매니저로 보냄 |

## 7. 한계

- **고객 운영 장시간 미측정.** CIC-IDS2017은 2017년 테스트베드라 현재 트래픽(TLS 1.3, QUIC, 클라우드 서비스)과 다르다. TLS 비커닝·원격 실행·머신 계정 사용·AI·AD 탐지는 실제 업무 트래픽의 오탐을 아직 재지 않았다. 확산·원격 실행·AD 정보 수집처럼 관리 서버·점검 도구 예외가 필수인 룰은 배포 설정에 크게 좌우된다.
- **심각도 미구분.** 단일 탐지의 심각도가 모두 `Information`이라 DCSync·랜섬웨어도 스캔과 같은 등급으로 나간다.
- **비콘 오탐.** CIC에서 남은 오탐 19건 중 15건이 광고·뉴스 주기 통신이다. 예외로 하나씩 쫓기 어렵다.
- **탐지 범위 밖.** DoS·DDoS는 탐지하지 않는다. HTTPS로 받은 파일의 악성 여부는 보지 않는다.
- **암호화 구간.** SMB3 암호화 세션(05·06·21), TLS 1.3 인증서(09 자체서명 신호), DNS over HTTPS, 암호화 RPC, HTTPS 웹서버(03·04·28·29)는 볼 수 없다.
- **조건 아래의 공격.** 5분 25포트 미만의 느린 스캔, AES 티켓만 요청하는 Kerberoasting, 덮어쓰기·대량 삭제형 랜섬웨어, HTTP 안의 NTLM(05·19), 10대 미만 AD 정보 수집, 30분 안에 끝나는 TLS 비콘은 놓친다.
- **클러스터 한계.** 22 NBNS는 질의와 응답이 다른 워커로 가면 놓친다. 23 DCSync·33 서버 판별·34 spoolss의 DC·서버 학습은 워커별이라 목록 설정을 권장한다. 사건 묶기는 탐지를 낸 노드별이다.
- **연동 미완료.** OCSF 변환기가 2차 신규 탐지와 영향 단계를 모르고, 자산 식별 결과(서버 역할)를 예외에 자동 반영하지 못한다.

전체 목록과 대응 계획은 SRS 10장과 [NSM_RULES_REVIEW.md](NSM_RULES_REVIEW.md) 5장에 있다.

## 부록 B. pcap 탐지 점검 방법

`tests/run_pcap.sh <pcap 또는 디렉터리>`가 운영과 같은 설정으로 Zeek를 실행하고, 탐지 종류별 건수·출발지 수를 자산 신호·선별 전송 요약과 함께 출력한다. 탐지·근거·킬체인·자산·전송량·예외·센서 상태를 묶은 통합 리포트(`<pcap 이름>_report.html`)도 만든다. 예외 파일을 넣어 실행하면 예외 적중 수와 남은 탐지를 함께 볼 수 있다.

- 정상 트래픽만 있는 날(CIC-IDS2017 월요일)이나 고객 첫 주 캡처에서 나오는 탐지는 대부분 오탐 후보다. 건수가 많은 룰부터 근거(`evidence.log`)를 보고 예외 파일이나 임계를 조정한다.
- 결과에는 주소·호스트명·계정 원문이 들어 있어 고객사 밖으로 내보내지 않는다.

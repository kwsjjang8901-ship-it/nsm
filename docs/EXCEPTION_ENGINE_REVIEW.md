## 요약

제안의 방향(예외를 코드가 아니라 데이터로, 공통 축, 사유·작성자·만료일 필수, 억제 단계 구분)은 맞고 진행할 가치가 있다. 다만 지금 코드에 그대로 옮기면 세 군데가 문제가 되므로 수정해서 진행한다.

1. **판정 지점을 옮겨야 한다.** `Notice::policy` 훅에서만 판정하면 집계형 룰의 (출발지, 목적지) 쌍 예외를 처리할 수 없고, 근거가 notice보다 먼저 기록돼 버린다(3.1절). 결정: 룰 입구에서 공통 함수로 판정한다.
2. **억제(suppress)를 기본값으로 하면 지금 계약(예외 대상은 기록하지 않음)과 Manager 로그량이 바뀐다**(3.5절). 결정: 기본은 기존과 같은 `drop`, `suppress`는 예외별 선택.
3. **예외에 쓰는 자산 그룹은 사람이 승인한 것만 쓴다.** 자동 추정 그룹을 예외에 쓰면 공격자가 예외를 얻는 경로가 된다(3.3절).

센서 쪽 개발은 약 6–7주로 추정한다(5장). 예외 29개를 옮기는 비용이 아직 작아 지금 하는 것이 맞고, AI 예외 추천은 이 엔진 위에 올린다.

## 결정 사항 (2026-11-11)

권장안 D1–D4를 바탕으로, 현재 SRS와의 비교에서 나온 계약 충돌을 아래처럼 정리했다. 이 절이 본문의 앞선 검토 내용보다 우선한다.

| 번호 | 결정 | 이유 |
| --- | --- | --- |
| 처리 기본값 | **`drop`(기존 스펙 유지).** 예외 대상은 notice·근거·탐지 요약을 남기지 않는다. 기존 `*_allowlist`도 `drop`으로 옮긴다 | Manager 로그량을 지금과 같게 유지. `suppress` 기본이면 지금 0건인 로그가 생긴다(5분 창 스캐너 하나면 하루 notice 288건, 근거 최대 5,760행) |
| `suppress` | 예외별로 선택하는 옵션. 새 예외의 관찰 기간, 위험도가 높은 경로처럼 기록을 남겨 확인할 때만 쓴다 | 쓰는 곳이 적어 양이 문제되지 않음 |
| 판정 지점 | **룰 입구 한 곳.** 지금 allowlist를 검사하는 자리를 공통 함수 한 줄(`NSM::exception_drop(note, c)` 등)로 바꾼다 | 근거는 notice보다 먼저 기록되므로(FR-C2) notice 시점 `drop`이면 근거만 남는다. 룰 입구에서는 연결 정보로 모든 축(src·dst·포트·서비스·SNI·JA4)을 얻을 수 있다 |
| 집계형 룰의 쌍 예외 | `suppress`로 지정해도 `drop`으로 동작(적중 수만 기록) | notice가 생기지 않으므로 "기록하되 알림 없음"이 성립하지 않음(3.1절) |
| D1 Manager 전송 | 예외 통계 로그는 항상 보낸다. 억제된 탐지 행은 `suppress`를 켠 예외에서만 생기며 1건씩 보낸다(`disposition=suppressed`) | notice 1건 = 탐지 요약 1행(FR-C3), notice와 근거 조인(NFR-11) 계약 유지 |
| D2 킬체인 상관 | `suppress` 예외에만 해당. 억제된 탐지는 상관에 넣되 억제된 단계만으로는 체인 알림을 만들지 않는다. E5 전까지는 상관에서 제외(보수적) | `drop`은 지금처럼 상관에도 없음 |
| D3 범위 지정 | notice 이름과 기존 상관 단계 묶음(`corr_*_notes`) | |
| D4 downgrade | 이번 범위에서 제외 | 심각도가 모두 `Information` 고정 |

### `drop` 유지의 대가와 보완

| 잃는 것 | 보완 |
| --- | --- |
| 예외 대상 세션이 탐지 쪽에서 보이지 않음 | 메타데이터 선별 전송은 탐지 예외와 무관하게 동작(자체 예외 목록 `meta_domain_allowlist`만 적용). 흐름 요약·SSL·HTTP·Kerberos 등으로 소급 검색 |
| 예외가 막은 양 | 예외 통계 로그. 단, 적중 수는 "막은 탐지 건수"가 아니라 **"예외에 걸린 관측(연결·이벤트) 수"** 다. 대시보드에 단위를 명시한다 |
| 잘못된 예외 발견 | 통계의 0건·급증, 만료 필수, 넓은 예외 거부, 필요한 예외만 `suppress` |
| 예외 경로를 쓴 확산이 킬체인에 안 이어짐 | 지금과 같음(회귀 아님). 다음 단계(유출 등)는 단일 탐지로 잡힌다 |
| 룰 코드에서 예외 코드가 완전히 사라지지 않음 | 룰마다 공통 함수 한 줄. 예외 형식·축·동적 로딩·메타데이터 이점은 그대로 |

## 1. 검토 대상 제안 요약

| 항목 | 제안 내용 |
| --- | --- |
| 근본 원인 | 예외 판정이 각 룰 코드 안에 있어, 룰이 늘면 예외 메커니즘도 같이 늘어난다 |
| ① 룰 밖으로 | 룰은 조건을 만족하면 NOTICE만 낸다. 억제 여부는 `Notice::policy` 훅에서 공통 판정. 예외 테이블은 Input Framework로 동적 로딩(재시작 없이 반영) |
| ② 축 통일 | 공통 축(`src`, `dst`(IP·대역·자산 그룹), `service`, `domain`·`sni`, `ja4`, 세그먼트 쌍, 시간대)의 AND 조합으로만 예외를 표현. `scope`에 룰 또는 룰 그룹 |
| ③ 자산 그룹 | 개별 IP 대신 `scanners`, `backup-servers`, `jump-servers` 같은 그룹을 참조 |
| ④ 메타데이터 | 사유·작성자·만료일 필수. 만료일이 없으면 90일 후 재검토 알림, 근거 알림 ID 기록, 임시 예외는 만료 필수 |
| ⑤ 단계 구분 | `drop`(평가 생략, 제한적으로), `suppress`(기록하되 알림 없음, 기본값), `downgrade`(심각도만 낮춤). 예외별 억제 건수 대시보드 |
| 효과 | 룰별 튜닝 슬롯이 공통 축 1세트로 줄고, AI 룰 추천이 "예외 레코드 1건 생성"으로 단순해진다 |

```yaml
  expires: null
  owner: kim

- scope: rule_group:lateral      # 15, 16 동시 적용
  match: { src_group: jump-servers, dst_group: server-farm, service: [rdp, ssh] }
  reason: 운영팀 정상 접근 경로
  expires: 2027-06-30
  owner: lee
```

## 3. 항목별 검토

### 3.1 예외 판정을 룰 밖으로 — 채택, 판정 지점은 둘

**건별 룰**(03·04·09·10·12·19·23·24 등)은 notice 시점에 src·dst·포트·SNI가 모두 있으므로 `Notice::policy` 판정으로 충분하다. 룰 코드에서 예외 처리가 사라진다. 다만 notice에 SNI·도메인·JA4·서비스가 구조 필드로 실리지 않는 룰이 있어 **notice 공통 컨텍스트 필드**를 먼저 정해야 한다(5장 E2).

**집계형 룰**(스캔·스프레이·확산·비커닝·DNS·랜섬웨어 등)은 notice 시점 판정으로 해결되지 않는다.

- 예외 "점프 서버 → 서버팜 SSH"가 있을 때, 공격자가 점프 서버에서 서버팜 30대와 다른 host 2대에 접속하면 집계는 32대로 임계를 넘어 notice가 나온다.
- notice 시점에는 어느 목적지가 예외 경로였는지 알 수 없다(`lm_targets`도 표본 `lm_num_samples` 개까지만).
- notice 전체를 억제하면 진짜 2대를 놓치고, 억제하지 않으면 예외가 무력해진다.

따라서 판정 지점을 둘로 둔다. 예외 형식·매칭·통계는 하나다.

| 판정 지점 | 적용 대상 | 룰 코드 |
| --- | --- | --- |
| notice 시점(`Notice::policy`, 중복 묶기보다 먼저) | 건별 룰 전부, 집계형 룰의 출발지 단독 예외 | 없음 |
| 집계 직전(공통 함수) | 집계형 룰의 (출발지, 목적지) 쌍 예외 | 한 줄: `if ( NSM::exception_hit(SSH_Lateral, ctx) ) return;` |

**Input Framework 동적 로딩 — 채택.** 구현 조건:

- Input Framework는 YAML을 읽지 못한다. Manager가 YAML을 검증한 뒤 Zeek 입력 형식(TSV)으로 변환해 배포하고, 센서는 `Input::REREAD`로 변경을 감지한다.
- 파일 교체는 임시 파일에 쓴 뒤 이름 바꾸기(원자적 교체)로 한다. 센서는 읽기가 끝난 시점(`Input::end_of_data`)에 색인을 한 번에 바꾼다. 반쯤 읽힌 목록으로 판정하지 않기 위해서다.
- 클러스터에서는 Intel 프레임워크처럼 manager가 읽어 워커로 배포한다. 판정이 워커에서 일어나기 때문이다.
- 재시작 없는 변경만 급하다면 `const`를 `option`으로 바꾸고 Config 프레임워크를 쓰는 중간 방법도 있다. 클러스터 배포까지 되지만 사유·만료 같은 메타데이터는 담지 못한다. 이중 이관이 되므로 권장하지는 않는다.

### 3.2 예외 축 통일 — 채택, 범위 지정 방식 수정

- **범위는 룰 번호(`rule:09`)가 아니라 notice 이름(`Encrypted_C2`)으로 지정한다.** 한 파일에 notice가 여러 개라 번호로는 "08의 터널링만"을 지정할 수 없다. notice 이름은 탐지 로그·XDR 연동에서 이미 식별자로 쓰인다.
- **룰 그룹은 이미 있다.** 상관분석의 단계 묶음(`corr_lateral_notes`, `corr_exfil_notes`, `corr_cred_notes` 등)을 그대로 쓰면 그룹 정의가 한 곳에서 관리된다.
- **JA4 축은 조건부다.** 기본 `get_ja4`가 빈 문자열을 반환하므로, JA4 패키지가 없는 센서에서 JA4 조건이 들어간 예외는 아무것도 맞지 않는다. 센서는 이런 예외를 "적용 불가"로 보고한다.
- **시간대 축은 제한해서 넣는다.** 공격자에게 "이 시간에는 안 보인다"는 창을 만들어 준다. 시간대 예외는 만료일 필수로 한다.
- **너무 넓은 예외는 검증 단계에서 거부한다.** 예: 범위가 전체인 예외, 축 하나에 /16보다 넓은 대역만 있는 예외. 축이 통일되면 이 규칙을 한 곳에서 걸 수 있다.

### 3.3 자산 그룹 — 채택, 그룹 출처 구분

- 중복 제거와 IP 변경 대응 효과는 제안대로다.
- **예외에 쓰는 그룹은 사람이 승인한 그룹이어야 한다.** 자산 식별은 관측 트래픽으로 역할을 추정한다. 공격자가 자기 host를 스캐너나 백업 서버처럼 보이게 만들면 그룹에 들어가 예외 혜택을 받는다. 자동 추정은 그룹 후보를 제안만 하고, 승인 후 반영한다.
- 환경 사실(DC, DNS 서버)은 자동 추정을 써도 위험이 작다. 탐지를 넓히는 쪽이기 때문이다. 예외는 탐지를 좁히는 쪽이라 기준이 달라야 한다.
- 그룹 멤버십도 예외와 같은 Input 경로로 센서에 동적으로 내려보낸다.

### 3.4 사유·작성자·만료일 필수 — 그대로 채택

- 센서는 만료된 예외를 **적용하지 않고** 상태 로그에 만료로 보고한다. 삭제와 재검토 알림은 원본 YAML을 가진 Manager가 맡는다.
- 근거 알림 ID는 탐지 로그의 `detection_id`를 쓴다.

### 3.5 drop·suppress·downgrade — 채택, 의미를 구조에 맞게 정의

| 단계 | 의미 |
| --- | --- |
| `drop` | 지금 allowlist와 같은 동작(집계 전 제외). 예외별 적중 수만 센다 |
| `suppress`(기본) | notice.log와 근거(evidence)는 남긴다. 탐지 로그에 `disposition=suppressed`와 `exception_id`를 붙이고, Manager는 알림을 올리지 않는다 |
| `downgrade` | 지금은 의미가 없다. 심각도가 모두 `Information` 고정이라 심각도 모델이 먼저 필요하다 |

함께 정할 것:

- **억제된 탐지를 킬체인 상관에 넣을지.** 권장은 "넣되, 억제된 단계만으로는 체인 알림을 만들지 않고 억제되지 않은 단계가 이어지면 체인에 포함"이다. 점프 서버가 장악돼 예외 경로로 확산한 뒤 유출하는 경우를 잡으려면 필요하다. 지금은 중복 묶기에서 로그 액션이 빠진 notice가 상관분석(`Notice::log_notice`)에 들어가지 않으므로 이 경로를 손봐야 한다.
- **억제 건수 대시보드의 원천.** 억제된 탐지를 건별로 모두 Manager에 보내면 바쁜 예외(스캐너 등)가 전송량을 늘린다. 선별 전송 통계(`meta_export_stats`)처럼 **예외별 적중 수·마지막 적중 시각을 주기 로그로** 보내고, 억제 탐지 행은 표본만 보내는 것을 권장한다. 30일 0건 예외와 급증 예외는 이 로그로 Manager가 판단한다.

## 5. 개발 단계 (센서 쪽, 추정)

| 단계 | 내용 | 기간 |
| --- | --- | --- |
| E1 엔진 코어 | 예외 레코드 형식, Input 로딩(REREAD, manager→워커·프록시 배포), 색인·매칭, 룰 입구 판정 함수, `drop`·`suppress` 처리(suppress는 notice 표시), 만료, 예외 로그, 시범 이관(09 건별·16 집계형), 테스트 | 2주 |
| E2 공통 컨텍스트 | 룰 입구에서 연결로 축을 얻으므로 대부분 불필요. 연결이 없는 룰(DNS 집계 등)의 컨텍스트만 보강 | 0.5주 |
| E3 이관 | 건별 룰의 예외 코드 제거, 집계형 룰은 공통 함수 한 줄로 교체, 기존 설정 자동 변환, 동작 일치 테스트 | 2주 |
| E4 자산 그룹 | 수동 그룹부터. 자산 식별 머지 후 자동 후보 + 승인 | 1–2주(자산 식별 머지 후) |
| E5 상관분석 연동 | `suppress` 예외의 킬체인 처리(D2). E5 전까지 억제된 탐지는 상관에서 제외 | 0.5주 |

센서 쪽 합계 약 6–7주. Manager 쪽(YAML 스키마·검증·변환·배포·대시보드·재검토 알림)은 이 저장소 밖이라 별도로 잡는다.

"룰이 30–50개가 되기 전에 하는 것이 싸다"는 판단에 동의한다. 지금 이관 대상은 예외 29개, E3 약 2주다. AI 예외 추천은 E1–E3 이후에 올린다.

## 1. 요약

| 항목 | 결과 |
| --- | --- |
| 기능 구현 | 탐지 결과 외에 조사·헌팅용 메타데이터를 골라 `/log/zeek/meta/`(JSON)에 기록하는 센서 모듈 완성. 행 단위 9종(Kerberos, NTLM, SMB 공유·파일, 주요 RPC, RDP, SSH, SSL, HTTP), 요약 3종(흐름, DNS, HTTP User-Agent), 센서 상태·선별 통계 |

| 처리 부하(목표: 선별 전송 끔 대비 5% 이하) | 신뢰할 수 있는 측정은 +4.0\~5.1%. 같은 조건 +13.8% 측정이 있어 **확정하지 못함**. 측정 스크립트는 구성을 번갈아 실행하도록 고침(#46), 재측정 대기 |

**결론:** 선별 전송 구조(센서에서 거르기, 요약, 과부하 안전장치)는 PoC 목표대로 동작하고, 공개 데이터셋 5일에서 하루 수십 MB 수준으로 탐지 후 조사에 쓸 수 있음을 리포트로 확인했다. 다만 "전체 로그 대비 %"는 캡처 길이·구간에 따라 크게 흔들려 운영 판단 기준으로 불안정하므로, 센서당 하루 전송량 같은 절대량 기준을 함께 두는 결정이 필요하다. **고객 운영 구간의 1시간 이상 측정(DC 포함)과 처리 부하 재측정**이 남아 있다.

## 2. 목적과 범위

센서는 탐지 결과만 보내고 프로토콜 로그는 모두 끄고 있었다. 그래서 탐지 앞뒤 맥락 확인, 근거(`uid`)와 원본 조인, 탐지 룰이 없는 위협의 사후 헌팅이 불가능했다. 반대로 Zeek 로그를 전부 보내면 운영 구간 기준 하루 약 180GB 규모라 현실적이지 않다(자산 식별 PoC 측정: 200초에 423.5MB).

| 구분 | PoC 범위 | 범위 밖 |
| --- | --- | --- |
| 센서 | 선별 전송 모듈(`nsm_rules/metadata/`), 설정, 회귀 테스트, 측정 도구 | 수집 에이전트, Manager 저장·조회 |
| 연동 | 출력 형식 정의(SRS 5장), 통합 리포트에서 탐지 근거와 조인 | 수집 에이전트·Manager 연동, OCSF 변환기(다음 단계). 자산 신호는 별도 로그로 전송 |

목표(2026-11-10 확정):

| 지표 | 목표 |
| --- | --- |
| 전송량 | Zeek 전체 로그 대비 5% 이하 |
| 처리 부하 | 선별 전송 끔 대비 처리 시간 증가 5% 이하 |
| 탐지 영향 | 탐지 결과·근거는 100% 기록 |
| 과부하 | 상한을 넘으면 버리고 건수를 기록 |
| 개인정보 | URL 쿼리 문자열·인증값은 보내지 않음 |

### 3.2 구조

| 계층 | 내용 | 전송 |
| --- | --- | --- |
| T0 탐지 | notice, nsm_detection, evidence | 항상(기존 그대로) |
| T1 선별 메타데이터 | 이번 PoC. 행과 필드를 줄인 프로토콜 로그와 요약 로그 | 전송 |
| T2 원본 | 줄이지 않은 Zeek 로그 | 선택 기능, 센서 로컬 보관(기본 끔) |

- 스트림마다 로그 필터를 하나 더 붙이고, 행마다 범위(방향·관리 포트) → 스트림별 조건 → 중복 억제 → 노드당 분당 상한 순으로 판정한다.
- 판정은 로그를 쓰는 워커에서 한다. 탈락한 행은 직렬화·로거 전송·디스크 쓰기를 하지 않는다(클러스터 테스트로 확인).
- 양이 큰 conn·DNS와 HTTP User-Agent는 행 대신 노드 메모리에서 묶어 주기마다 요약 행을 쓴다.
- 통계 로그(`meta_export_stats`)에 스트림별 보냄·탈락 사유별·요약 건수를 5분마다 남긴다.
- 자산 신호(`asset_signal.log`)와 탐지 로그는 이 모듈과 별도 경로(`/log/zeek/`)로 Manager에 간다.

### 3.3 출력 로그 (현재 기본값)

| 로그 | 종류 | 범위·선별 | 주기·중복 억제 |
| --- | --- | --- | --- |
| kerberos, ntlm, rdp, ssh | 행 | 전체 | 없음 |
| smb_mapping | 행 | 전체 | 1시간 |
| smb_files | 행 | 쓰기·이름 변경·삭제만 | 10분 |

| ssl | 행 | 내부↔외부, 예외 도메인 제외 | 24시간 |
| http | 행(User-Agent 제외, 쿼리 문자열 제거) | 내부↔외부, 예외 도메인 제외 | 10분 |

| capture_loss, stats, reporter, meta_export_stats | 센서 상태 | | |

- 모두 JSON 한 줄 한 행이다. 목록 값(`flow_summary.service`, `dns_summary.qtypes`, `sample_names`, `answers`)은 JSON 배열이고, 건수가 붙은 값(`states`, `rcodes`)은 문자열이다.

## 5. 측정 방법

`tests/measure_meta_export.sh <pcap> [반복]`이 같은 pcap을 세 구성으로 실행해 비교한다.

| 구성 | 내용 |
| --- | --- |
| full | nsm_rules 없이 Zeek 전체 로그(JSON) |
| off | nsm_rules, 선별 전송 끔 |
| on | nsm_rules, 선별 전송 켬 |

- 출력: 선별 로그별 바이트·행 수, 전체 대비 비율, off 대비 on 처리 시간 증가율(반복 중 최솟값).
- PR #33부터 조정 근거도 출력: 로그별 필드 비중, 요약 로그의 키 분포. 주소·도메인 원문은 출력하지 않는다.
- 11-11 이후 개선(#46): 구성을 회차마다 번갈아 실행하고 같은 회차 쌍의 증가율 중앙값·범위로 처리 부하를 보고한다(6.2절의 흔들림 대응). 압축 후 크기와 조정 후보(③·⑩) 추정도 출력한다. 처리 부하와 ③·⑩ 판단은 이 방식으로 다시 측정한다.
- 측정 환경: 사용자 VM. pcap을 VM 공유 폴더(`/mnt/hgfs`)에서 읽으면 처리 시간이 수십 초씩 흔들려, 로컬 디스크 측정만 부하 판단에 썼다.

## 6. 측정 결과

6.1\~6.4절은 2026-11-11 시점(#33 형상) 측정이다.

### 6.1 전송량

| 단계 | CIC-IDS2017(8시간) | eth5 | eth5(16) |
| --- | --- | --- | --- |
| 초기(P3 기본값) | 35.35MB, **7.27%** | | |
| 1차 조정(#32) | 30.55MB, **6.28%** | 7.29MB, **8.08%** | 6.44MB, **5.36%** |
| 2차 조정(#33) | 25.08MB, **5.16%** | 5.83MB, **6.46%** | (미측정) |

2차 조정 후 로그별 크기:

| 로그 | CIC-IDS2017 | eth5 |
| --- | --- | --- |
| flow_summary | 9.08MB (36%) | 2.03MB (35%) |
| http + http_ua_summary | 7.90MB (31%) | 1.12MB (19%) |
| ssl | 4.09MB (16%) | 0.36MB (6%) |
| dns_summary | 3.16MB (13%) | 2.29MB (39%) |
| AD 계열(kerberos·ntlm·smb·dce_rpc) | 0.39MB (2%) | 0.02MB |
| 그 밖(ssh·상태·통계) | 0.47MB (2%) | 0.00MB |

- 두 구간 모두 흐름·HTTP·DNS 요약이 대부분이다. AD 계열은 조사 가치가 크지만 양은 2% 이하라 줄일 필요가 없다.
- eth5는 몇 분짜리 캡처라 비율이 높게 나온다. 요약 로그는 같은 키가 반복될수록 줄지만, 전체 로그는 시간에 비례해 늘기 때문이다. 같은 구성에서 8시간인 CIC의 HTTP User-Agent 요약은 0.01MB, 수 분인 eth5는 0.20MB였다.
- 합성 pcap은 공격 트래픽 비중이 커서 18.81%로 나오며, 비율 판단에 쓰지 않는다.

- 추가 운영 캡처(1111\_00\~03)도 공유 폴더 측정이라 −1.1%에서 +19.0%까지 흩어졌다. 부하 판단에는 쓰지 않는다.

### 6.4 추가 운영 캡처 측정 (1111\_00\~03)

사용자가 운영 미러 캡처 4개를 2차 조정(#33) 형상으로 더 측정했다(공유 폴더, 3회). 캡처 시간은 기록하지 않았으므로 크기는 Zeek 전체 로그로 나타낸다.

| pcap | Zeek 전체 로그 | 선별 전송 | 비율 | `sample_uid` 정리 후(추정) |
| --- | --- | --- | --- | --- |
| 1111_00 | 68.95MB | 4.83MB | 7.01% | 6.34% |
| 1111_01 | 48.78MB | 4.97MB | 10.18% | 9.47% |
| 1111_02 | 10.38MB | 0.19MB | 1.86% | 1.66% |
| 1111_03 | 2.05MB | 0.61MB | 29.57% | 27.53% |
| (참고) CIC-IDS2017 8시간 | 486.47MB | 25.08MB | 5.16% | 4.81% |
| (참고) eth5 | 90.16MB | 5.83MB | 6.46% | 5.84% |

- 추정 방법: 흐름·DNS 요약 행 수 × 34바이트(`,"sample_uid":"<uid 18자>"`)를 뺐다. 스크립트가 출력한 필드 비중(flow 15\~16%, dns 10\~11%)과 맞는다. 정리 후 실측은 다음 측정에서 확인한다.
- **비율이 캡처마다 크게 다르다.** 1111\_02는 출발지가 21개뿐이라 요약이 잘 묶여 1.86%, 1111\_03은 전체 로그가 2MB인 아주 짧은 캡처라 29.57%다. 짧은 캡처는 요약 로그가 주기 끝까지 모이지 않은 채 종료 시점에 한꺼번에 기록되므로 비율이 부풀려진다.
- **트래픽 구성 영향.** 1111\_01은 http가 2.02MB(선별 전송의 41%)로 가장 크다. `uri_path`가 http 행의 27%이고 (출발지, Host) 조합당 평균 4.7행이라, 같은 Host의 다른 경로 요청이 각각 행이 된다. 1111\_00은 DNS 요약이 39%로 eth5와 비슷한 모습이다(출발지 3,007개, 출발지당 평균 2.0행).
- 1111\_03은 목적지 포트 50502·8293이 흐름 요약의 88%를 차지하는 특정 장비 구간이고, 내부↔내부 흐름이 없다.
- 이 결과로 보면 "Zeek 전체 로그 대비 %"는 캡처 길이와 구간에 따라 크게 달라져 운영 판단 기준으로 불안정하다. 센서당 하루 전송량(GB/일) 같은 **절대량 상한을 함께 두는 방안을 제안했으며 결정 대기**다.

### 6.6 Manager 전송 로그량 예측 (1,000명)

Manager로 가는 로그는 대역폭이 아니라 연결·목적지 수에 비례한다. CIC 금요일 8시간의 연결 기록(공격 트래픽 제외, 내부 PC·서버 14대)과 그날 Manager 전송 로그를 맞추면 **외부 연결 1만 건당 약 2.3MB**다. 선별 메타데이터가 전송량의 97.7%, 자산 신호 1.2%, 센서 상태 1.0%, 탐지 로그 0.1%다.

| 사용자(PC) 수 | 하루 외부 연결 | Manager 하루(압축 전) |
| --- | --- | --- |
| 100 | 65만 | 0.15GB |
| 1,000 | 650만 | 1.5GB |
| 10,000 | 6,500만 | 15GB |

- PC 1대가 8시간에 외부 연결 약 6,500건(CIC 평균)을 하루 사용량으로 놓았다. 업무용 SaaS가 많아 연결이 2배면 전송량도 2배라, 1,000명은 1.5\~3GB로 잡는다.
- HTTP와 AD 인증·SSH는 연결 수에 거의 비례하고, TLS·흐름·DNS는 목적지 종류 수에 비례한다. 내부 서버팜(DC·파일 서버)까지 미러하면 30\~50% 더 나올 수 있다.
- 트래픽 유형별 계수, 대역폭 기준 상한, 1년 스토리지 산정(ClickHouse 0.3\~0.6TB)은 통합 보고 [POC_RESULT.md](POC_RESULT.md)의 Manager 전송 로그량 예측·스토리지 산정 절에 있다.

## 9. 한계

- **비율 기준의 불안정.** 같은 형상에서 캡처에 따라 1.86%에서 29.57%까지 나왔다(6.4절). 장시간 캡처로도 구간별 차이는 남으므로 절대량 기준 검토가 필요하다.
- **운영 장시간 측정 없음.** 운영 미러 측정은 모두 수 분짜리라 요약 로그 비중이 실제보다 크게 나온다. 공개 데이터셋은 2017년 연구용 망이라 고객망 구성(TLS 1.3, QUIC, 클라우드 서비스)과 다르다.
- **DC 구간 미측정.** Kerberos·NTLM·SMB·RPC 로그량은 DC 트래픽이 많은 구간에서 확인하지 않았다(공개 데이터셋 기준 2% 이하).
- **처리 부하 측정.** 스크립트는 고쳤지만(#46) 고친 방식으로 다시 재지 않았다.
- **클러스터 실운영 미검증.** 클러스터 동작은 btest로만 확인했다. 워커별 중복 억제·요약으로 생기는 중복 행은 Manager에서 합치는 것으로 정했다.
- **Manager 측 미검증.** 출력 형식은 SRS로 정의했지만 수집 에이전트·Manager와 실제로 연동해 보지 않았다. ClickHouse 압축률도 경험값이다.
- **리포트 관측은 추정.** 메타데이터 관측은 출발지·대상·시간으로 맞춘 것이고, 평소 통신 판정은 리포트에 넣은 로그 기간 안에서만 본다. 내부 일반 포트 이동은 메타데이터에도 없다.
- **소급검색 공백.** 새 위협 지표를 과거 데이터에 대어 볼 때, 외부 IP·등록 도메인·SNI·JA3·계정은 찾을 수 있다. 파일 해시·인증서·하위 도메인은 보내지 않아 찾을 수 없다. 보강안은 [RETRO_SEARCH_DESIGN.md](RETRO_SEARCH_DESIGN.md)에 있다.

## 2. 목적과 범위

센서는 탐지 결과만 보내고 프로토콜 로그는 모두 끄고 있었다. 그래서 탐지 앞뒤 맥락 확인, 근거(`uid`)와 원본 조인, 탐지 룰이 없는 위협의 사후 헌팅이 불가능했다. 반대로 Zeek 로그를 전부 보내면 운영 구간 기준 하루 약 180GB 규모라 현실적이지 않다(자산 식별 PoC 측정: 200초에 423.5MB).

| 구분 | PoC 범위 | 범위 밖 |
| --- | --- | --- |
| 센서 | 선별 전송 모듈(`nsm_rules/metadata/`), 설정, 회귀 테스트, 측정 도구 | 수집 에이전트, Manager 저장·조회 |
| 연동 | 출력 형식 정의(SRS 5장) | 자산 식별 로그 포함, OCSF 변환기 연동(다음 단계 P4) |

목표(2026-11-10 확정):

| 지표 | 목표 |
| --- | --- |
| 전송량 | Zeek 전체 로그 대비 5% 이하 |
| 처리 부하 | 선별 전송 끔 대비 처리 시간 증가 5% 이하 |
| 탐지 영향 | 탐지 결과·근거는 100% 기록 |
| 과부하 | 상한을 넘으면 버리고 건수를 기록 |
| 개인정보 | URL 쿼리 문자열·인증값은 보내지 않음 |

- 통계 로그(`meta_export_stats`)에 스트림별 보냄·탈락 사유별·요약 건수를 5분마다 남긴다.

## 5. 측정 방법

`tests/measure_meta_export.sh <pcap> [반복]`이 같은 pcap을 세 구성으로 실행해 비교한다.

| 구성 | 내용 |
| --- | --- |
| full | nsm_rules 없이 Zeek 전체 로그(JSON) |
| off | nsm_rules, 선별 전송 끔 |
| on | nsm_rules, 선별 전송 켬 |

- 출력: 선별 로그별 바이트·행 수, 전체 대비 비율, off 대비 on 처리 시간 증가율(반복 중 최솟값).
- PR #33부터 조정 근거도 출력: 로그별 필드 비중, 요약 로그의 키 분포. 주소·도메인 원문은 출력하지 않는다.
- 이 보고 이후 개선: 구성을 회차마다 번갈아 실행하고 같은 회차 쌍의 증가율 중앙값·범위로 처리 부하를 보고한다(6.2절의 흔들림 대응). 압축 후 크기와 조정 후보(③·⑩) 추정도 출력한다. 처리 부하와 ③·⑩ 판단은 이 방식으로 다시 측정한다.
- 측정 환경: 사용자 VM. pcap을 VM 공유 폴더(`/mnt/hgfs`)에서 읽으면 처리 시간이 수십 초씩 흔들려, 로컬 디스크 측정만 부하 판단에 썼다.

## 6. 측정 결과

### 6.1 전송량

| 단계 | CIC-IDS2017(8시간) | eth5 | eth5(16) |
| --- | --- | --- | --- |
| 초기(P3 기본값) | 35.35MB, **7.27%** | | |
| 1차 조정(#32) | 30.55MB, **6.28%** | 7.29MB, **8.08%** | 6.44MB, **5.36%** |
| 2차 조정(#33) | 25.08MB, **5.16%** | 5.83MB, **6.46%** | (미측정) |

2차 조정 후 로그별 크기:

| 로그 | CIC-IDS2017 | eth5 |
| --- | --- | --- |
| flow_summary | 9.08MB (36%) | 2.03MB (35%) |
| http + http_ua_summary | 7.90MB (31%) | 1.12MB (19%) |
| ssl | 4.09MB (16%) | 0.36MB (6%) |
| dns_summary | 3.16MB (13%) | 2.29MB (39%) |
| AD 계열(kerberos·ntlm·smb·dce_rpc) | 0.39MB (2%) | 0.02MB |
| 그 밖(ssh·상태·통계) | 0.47MB (2%) | 0.00MB |

- 두 구간 모두 흐름·HTTP·DNS 요약이 대부분이다. AD 계열은 조사 가치가 크지만 양은 2% 이하라 줄일 필요가 없다.
- eth5는 몇 분짜리 캡처라 비율이 높게 나온다. 요약 로그는 같은 키가 반복될수록 줄지만, 전체 로그는 시간에 비례해 늘기 때문이다. 같은 구성에서 8시간인 CIC의 HTTP User-Agent 요약은 0.01MB, 수 분인 eth5는 0.20MB였다.
- 합성 pcap은 공격 트래픽 비중이 커서 18.81%로 나오며, 비율 판단에 쓰지 않는다.

- 측정 스크립트가 구성별로 몰아서 실행해(full 3회 → off 3회 → on 3회), VM 부하가 시간에 따라 바뀌면 특정 구성만 손해를 본다. off·on을 번갈아 실행하도록 고친 뒤 다시 재야 확정할 수 있다.
- 추가 운영 캡처(1111\_00\~03)도 공유 폴더 측정이라 −1.1%에서 +19.0%까지 흩어졌다. 부하 판단에는 쓰지 않는다.

### 6.4 추가 운영 캡처 측정 (1111\_00\~03)

사용자가 운영 미러 캡처 4개를 2차 조정(#33) 형상으로 더 측정했다(공유 폴더, 3회). 캡처 시간은 기록하지 않았으므로 크기는 Zeek 전체 로그로 나타낸다.

| pcap | Zeek 전체 로그 | 선별 전송 | 비율 | `sample_uid` 정리 후(추정) |
| --- | --- | --- | --- | --- |
| 1111_00 | 68.95MB | 4.83MB | 7.01% | 6.34% |
| 1111_01 | 48.78MB | 4.97MB | 10.18% | 9.47% |
| 1111_02 | 10.38MB | 0.19MB | 1.86% | 1.66% |
| 1111_03 | 2.05MB | 0.61MB | 29.57% | 27.53% |
| (참고) CIC-IDS2017 8시간 | 486.47MB | 25.08MB | 5.16% | 4.81% |
| (참고) eth5 | 90.16MB | 5.83MB | 6.46% | 5.84% |

- 추정 방법: 흐름·DNS 요약 행 수 × 34바이트(`,"sample_uid":"<uid 18자>"`)를 뺐다. 스크립트가 출력한 필드 비중(flow 15\~16%, dns 10\~11%)과 맞는다. 정리 후 실측은 다음 측정에서 확인한다.
- **비율이 캡처마다 크게 다르다.** 1111\_02는 출발지가 21개뿐이라 요약이 잘 묶여 1.86%, 1111\_03은 전체 로그가 2MB인 아주 짧은 캡처라 29.57%다. 짧은 캡처는 요약 로그가 주기 끝까지 모이지 않은 채 종료 시점에 한꺼번에 기록되므로 비율이 부풀려진다.
- **트래픽 구성 영향.** 1111\_01은 http가 2.02MB(선별 전송의 41%)로 가장 크다. `uri_path`가 http 행의 27%이고 (출발지, Host) 조합당 평균 4.7행이라, 같은 Host의 다른 경로 요청이 각각 행이 된다. 1111\_00은 DNS 요약이 39%로 eth5와 비슷한 모습이다(출발지 3,007개, 출발지당 평균 2.0행).
- 1111\_03은 목적지 포트 50502·8293이 흐름 요약의 88%를 차지하는 특정 장비 구간이고, 내부↔내부 흐름이 없다.
- 이 결과로 보면 "Zeek 전체 로그 대비 %"는 캡처 길이와 구간에 따라 크게 달라져 운영 판단 기준으로 불안정하다. 센서당 하루 전송량(GB/일) 같은 **절대량 상한을 함께 두는 방안을 제안했으며 결정 대기**다.

## 9. 한계

- **비율 기준의 불안정.** 같은 형상에서 캡처에 따라 1.86%에서 29.57%까지 나왔다(6.4절). 장시간 캡처로도 구간별 차이는 남으므로 절대량 기준 검토가 필요하다.
- **운영 장시간 측정 없음.** 운영 미러 측정은 모두 수 분짜리라 요약 로그 비중이 실제보다 크게 나온다. 공개 데이터셋은 연구용 망이라 고객망 구성과 다르다.
- **DC 구간 미측정.** Kerberos·NTLM·SMB·RPC 로그량은 DC 트래픽이 많은 구간에서 확인하지 않았다(공개 데이터셋 기준 2% 이하).
- **처리 부하 측정 방법.** 구성별로 몰아서 실행하는 방식이라 VM 부하 변화에 약하다.
- **클러스터 실운영 미검증.** 클러스터 동작은 btest로만 확인했다. 워커별 중복 억제·요약으로 생기는 중복 행은 Manager에서 합치는 것으로 정했다.
- **Manager 측 미검증.** 출력 형식은 SRS로 정의했지만 수집 에이전트·Manager와 실제로 연동해 보지 않았다.

# 센서 제어 스펙 (Manager → NSM 센서)

작성: 2026-11-26 · 상태: 1차 범위 스펙 · 관련: [탐지 SRS](SRS.md) 7장(설정), [로그 스키마](LOG_SCHEMA.md)(`nsm_sensor`·`nsm_exception`·`nsm_ioc`), [1차 범위 목업](../ui/mockup/mdsm_nsm_mockup_phase1.html)(관리 › NSM 룰 정책·NSM 예외·NSM 탐지 엔진), [Suricata 연동 설계](SURICATA_INTEGRATION_DESIGN.md) 6.3절(선별 룰셋)

## 0. 요약

MDS Manager가 센서의 동작을 바꾸는 길은 다섯 가지입니다. **룰 정책(사용 여부·기준값)과 탐지 엔진 업데이트는 센서를 다시 시작해 적용하고**, 예외·IOC·에이전트 정책은 지금처럼 재시작 없이 파일을 다시 읽습니다. 위험도는 Manager 쪽 값이라 센서에 보내지 않습니다.

| 바꾸는 것 | 센서에 가는 것 | 적용 | 적용 확인(`nsm_sensor.log`) |
| --- | --- | --- | --- |
| **룰 정책**(룰 사용 여부, 탐지 기준값) | `nsm_config_policy.zeek`(Zeek 스크립트, `redef`) | **재시작** | `rule_policy_version` |
| **탐지 엔진 업데이트**(행위 룰 패키지·선별 시그니처·IOC 정보) | 패키지 | 행위 룰은 **재시작**, 시그니처는 Suricata 룰 다시 읽기, IOC는 파일 다시 읽기 | `pkg_version`, `ioc_sha1` |
| 예외 | 예외 파일(TSV, SRS 7.8) | 재시작 없음(파일 다시 읽기, 1분 안) | `exc_sha1` |
| IOC 정보(엔진 업데이트와 별개로 바꿀 때) | IOC 파일(TSV) | 재시작 없음 | `ioc_sha1` |
| 에이전트 정책 | 에이전트 정책 파일 | 재시작 없음 | `policy_sha1` |
| 위험도(룰별 Critical·High 등) | 보내지 않음(Manager 표시값) | 즉시(Manager) | - |

**재시작으로 정한 이유:** 탐지 기준값의 약 3분의 1(집계 구간·집계 임계 27개)은 Zeek 집계 구조(SumStats)를 만들 때 굳어 어차피 재시작이 필요합니다. 모든 룰 정책을 같은 방식으로 다루면 Manager·센서 구현과 화면 안내가 하나로 단순해집니다. 재시작 없는 적용의 검토 결과는 9장에 남깁니다.

## 1. 룰 정책 파일 `nsm_config_policy.zeek`

### 1.1 위치와 로드 순서

`nsm_rules/detections/nsm_config_policy.zeek`. 저장소에서는 비워 두고(주석만), Manager가 센서마다(정책 그룹마다) 만들어 바꿔 넣습니다.

`__load__.zeek`가 `nsm_config_fixed` → `nsm_config_custom` → **`nsm_config_policy`** 순으로 읽으므로 **값의 우선순위는 정책 > 고객 설정 > 제품 기본값 > 룰 파일 기본값**입니다. 설치 때 쓴 고객 설정(내부망 등)은 그대로 두고, 화면에서 바꾼 값만 정책 파일이 덮습니다.

### 1.2 내용

Manager가 쓰는 것은 세 종류뿐입니다. `@load`·함수·이벤트는 쓰지 않습니다.

| 줄 | 형식 | 뜻 |
| --- | --- | --- |
| 정책 버전 | `redef NSM::rule_policy_version = "<버전>";` | **필수.** 센서가 상태 로그로 보고해 적용을 확인하는 값(3장 5단계) |
| 끌 룰 | `redef NSM::disabled_rules += { "<룰>", ... };` | 끌 룰이 있을 때만. 룰 이름은 `nsm_detection.rule` 값과 같음(LOG_SCHEMA "룰과 진단명", 예: `Port_Scan`) |
| 기준값 | `redef NSM::<이름> = <값>;` | 화면에서 기본값과 다르게 정한 값만. 이름·타입·표기는 SRS 7.2·7.4·7.5절 |

```zeek
##! MDS Manager 생성 · 정책 그룹 "본사 센서" · 2026-11-26 10:42 · admin
redef NSM::rule_policy_version = "RP-HQ-20261126-3";
redef NSM::disabled_rules += { "Port_Scan", "Host_Scan" };
redef NSM::beacon_min_hits = 16;
redef NSM::krb_spray_user_threshold = 15;
redef NSM::lm_mgmt_allowlist += { 10.20.30.5, 10.20.30.6 };
```

- **버전 형식(권장):** `RP-<정책 그룹>-<YYYYMMDD>-<일련번호>`. 정책 그룹마다 늘어나는 값이면 무엇이든 됩니다.
- **전체를 새로 씀:** 바뀐 줄만 고치지 않고 매번 파일 전체를 만듭니다(같은 입력이면 같은 파일, 줄 순서 고정).
- **기본값과 같은 값은 쓰지 않음:** 패키지가 바뀌어 기본값이 달라질 때 고객이 고르지 않은 값이 남지 않게 합니다.

### 1.3 룰 끄기의 동작(센서)

끈 룰은 룰 파일을 고치지 않고, 모든 탐지가 지나는 공통 지점 네 곳에서 막습니다(구현: `nsm_rules/detections/main.zeek`의 `rule_disabled`·`disabled_notes`).

| 지점 | 효과 |
| --- | --- |
| 예외 입구(`exception_drop`·`exception_drop_agg`) | 룰이 계산을 시작하지 않음(건별 판정·SumStats 관측 생략) |
| 억제 확인(`notice_suppressed`) | 근거를 쓰기 전에 멈춤 |
| 근거 기록(`write_evidence`) | 근거만 남는 행이 생기지 않음 |
| notice 처리 훅(`Notice::policy`, 가장 먼저) | 남은 경로까지 모두 버림. 탐지 요약(`nsm_detection`)·ATT&CK·예외·묶기·**킬체인 상관**에 들어가지 않음 |

- 룰별 `detect_*` 스위치(28개)는 호환용으로 남습니다. 둘 중 하나라도 끄면 꺼집니다. Manager는 `disabled_rules`만 씁니다.
- 끈 룰이 체인의 한 단계였다면 그 단계 없이 나머지 단계로 체인이 이어집니다(btest `rules/rule-policy`: 포트 스캔·SQL 인젝션·랜섬웨어를 끄면 체인은 초기 침투~정보 유출 5단계).
- **모르는 룰 이름**(다른 패키지 버전의 룰 등)은 센서가 시작 경고를 내고 건너뜁니다. 3장 5단계에서 경고가 있으면 실패로 보므로, Manager가 쓰기 전에 걸러야 합니다(5장).

## 2. Manager 화면과 데이터

| 화면 동작 | Manager가 하는 일 |
| --- | --- |
| 룰 사용 여부·기준값 바꾸기 | 정책 그룹의 "배포 안 한 변경"으로 저장(센서에 보내지 않음) |
| 위험도 바꾸기 | Manager 값만 바꿈. **배포·재시작 없이 바로 반영** |
| 바뀌는 내용 보기 | 현재 배포본과 새 정책 파일의 차이, "센서 재시작 필요" 여부 |
| 배포(지금 / 예약) | 정책 파일을 만들어 3장 절차로 그룹의 센서마다 적용 |
| 배포 기록 | 버전, 시각, 작업자, 센서별 결과(적용·실패·되돌림), 실패 이유 |

배포 확인 창에는 "센서를 다시 시작합니다. 진행 중인 집계(스캔·스프레이·확산 등), 비커닝 추적, 킬체인 상관이 처음부터 다시 쌓이고, 재시작하는 동안(단독 수 초, 클러스터 수십 초) 패킷을 보지 못합니다"를 보여 줍니다(4장).

## 3. 배포 절차 (센서마다)

센서의 배포 에이전트(설치 패키지에 포함, 센서 관리 계정으로 실행)가 Manager의 지시를 받아 수행합니다.

| 단계 | 하는 일 | 실패하면 |
| --- | --- | --- |
| 1. 받기 | 새 정책 파일과 버전을 받아 임시 위치에 둠 | 실패 보고, 그대로 |
| 2. 검사 | 현재 파일을 `nsm_config_policy.zeek.bak`으로 두고 새 파일로 바꾼 뒤 `zeek -a <nsm_rules>`(구문만 읽기, 실행 중인 Zeek에는 영향 없음) | 곧바로 `.bak`으로 되돌리고 "검사 실패" + 오류 줄 보고. **재시작하지 않음** |
| 3. 재시작 | 단독은 서비스 재시작, 클러스터는 `zeekctl deploy` | 4단계로 |
| 4. 시작 확인 | 종료 코드, 시작 출력의 경고·오류 줄(경고 1줄도 실패로 봄. CI와 같은 기준) | 5단계 건너뛰고 되돌림 |
| 5. 적용 확인 | **2분 안에** 모든 노드의 `nsm_sensor.log`에 새 `rule_policy_version`이 옴(1분 주기 행) | 되돌림 |
| 되돌림 | `.bak`을 다시 넣고 재시작, 이전 버전이 보고되는지 확인 | "되돌림 실패"로 긴급 보고(장비 현황 위험) |
| 완료 | `.bak` 지움, "적용" 보고 | |

- **변경이 없으면 재시작하지 않음:** 새 파일이 지금 파일과 같으면(내용 해시) 1단계에서 끝냅니다.
- **한 번에 하나:** 같은 센서에 배포가 진행 중이면 다음 배포는 기다립니다. 탐지 엔진 업데이트(6장)와도 겹치지 않게 합니다.
- **정책 그룹 안에서는 차례로:** 그룹의 센서를 한 대씩(또는 정한 수만큼) 적용하고, 실패하면 나머지는 멈추고 관리자에게 묻습니다.
- **예약 배포:** "지금" 또는 지정 시각. 재시작 손실(4장)을 줄이려고 업무 외 시간을 권합니다.

## 4. 재시작의 영향

재시작하면 메모리에 쌓인 상태가 모두 처음부터 다시 쌓입니다. 탐지 로그는 이미 Manager로 갔으므로 사라지지 않습니다.

| 다시 쌓이는 것 | 영향 |
| --- | --- |
| 집계 창(스캔·스프레이·확산·대입 1~10분, 웹·AI 업로드 1시간, 누적 유출 등) | 재시작 앞뒤로 나뉜 공격은 기준에 못 미칠 수 있음 |
| 비커닝 추적(HTTP 12회 연속, TLS 30분 이상) | 진행 중이던 비콘은 처음부터 다시 셈 |
| 킬체인 상관(진행 중인 체인) | 재시작 전 단계와 후 단계가 한 체인으로 이어지지 않음. Manager 사건 묶기가 일부 보완 |
| 근거 중복 표, 억제 창 | 재시작 직후 같은 근거·notice가 한 번 더 나올 수 있음(Manager 사건 묶기로 합쳐짐) |
| DC 자동 학습(`dcsync_learn_dcs`) | 다시 학습. DC 목록을 설정했으면 영향 없음 |
| 재시작 중 패킷 | 단독 수 초, 클러스터 수십 초 동안 보지 못함 |

Manager는 `nsm_sensor.log`의 `uptime_s`가 줄어든 것으로 재시작을 알고, 장비 현황·탐지 목록 시간축에 재시작 구간을 표시합니다.

## 5. Manager가 쓰기 전에 검사할 것

센서는 문법 오류·모르는 이름에서 시작에 실패하거나 경고를 내므로, Manager가 먼저 걸러 배포 실패를 줄입니다.

| 검사 | 기준 |
| --- | --- |
| 룰 이름 | 센서 패키지 버전(`pkg_version`)의 룰 목록(LOG_SCHEMA "룰과 진단명")에 있음 |
| 기준값 이름·타입 | 그 패키지 버전의 기준값 표(SRS 7.4·7.5절). 화면에 노출하는 값만 허용 |
| 값 범위 | 건수·바이트는 1 이상 정수, 비율은 0~1, 시간은 단위 표기(`5min`, `3600sec`), 주소·대역·포트 형식 |
| 필수 값 | DC 주소·관리 서버(화면 "꼭 입력")가 비어 있으면 경고 |
| 버전 | 정책 그룹 안에서 이전보다 큼 |

Manager는 패키지 버전마다 룰 목록과 기준값 표(이름·타입·기본값·재시작 여부)를 들고 있어야 합니다. 이 표는 탐지 엔진 업데이트 패키지에 함께 넣어 보냅니다(6장).

## 6. 탐지 엔진 업데이트

| 대상 | 패키지 | 적용 | 확인 |
| --- | --- | --- | --- |
| 네트워크 행위 룰 | `nsm_rules` 디렉터리 전체 + 룰 목록·기준값 표(JSON) | 패키지를 바꾸고 **재시작**(3장과 같은 절차, 검사는 새 패키지 + 현재 정책 파일로) | `pkg_version` |
| 시그니처 룰(선별) | 선별 룰셋(`suricata.rules`, SID·rev 목록, 버전) | Suricata 룰 다시 읽기(`reload-rules`, 재시작 없음) | 센서 Suricata 상태(surica `suricata_stats`) |
| IOC 정보 | IOC 파일(TSV) | 파일 바꾸기(1분 안 다시 읽음) | `ioc_sha1`, `nsm_ioc` 적재 행 |

- **보존하는 파일:** 행위 룰 패키지를 바꿀 때 `nsm_config_custom.zeek`, `nsm_config_policy.zeek`, 예외 파일, IOC 파일은 그대로 둡니다.
- **호환 검사:** 새 패키지의 룰 목록·기준값 표로 현재 정책 파일을 먼저 검사합니다(5장). 없어진 룰·기준값이 있으면 Manager가 정책을 고친 새 버전을 만들어 패키지와 함께 배포합니다.
- **되돌리기:** 이전 패키지를 한 벌 보관하고, 실패하면 3장 되돌림과 같은 방식으로 돌아갑니다. 화면의 "이전 버전으로 되돌리기"도 같은 경로입니다.

## 7. 센서 쪽 구현 (이번 범위)

| 항목 | 위치 |
| --- | --- |
| `NSM::disabled_rules`(`const`, `redef` 가능), `NSM::rule_policy_version` | `nsm_rules/detections/main.zeek` |
| 공통 차단 지점 네 곳 | `main.zeek`(`notice_suppressed`·`Notice::policy` &priority=100), `exceptions.zeek`(`exception_drop*`), `evidence_log.zeek`(`write_evidence`) |
| 정책 파일 자리와 로드 순서 | `nsm_rules/detections/nsm_config_policy.zeek`(빈 파일), `nsm_rules/__load__.zeek` |
| 버전 보고 | `nsm_rules/sensor/status.zeek` → `nsm_sensor.log` `rule_policy_version` |
| 테스트 | btest `rules/rule-policy`(Zeek 9.0.1·8.0.9) |

배포 에이전트(3장)와 Manager 화면은 이 저장소 밖입니다.

## 8. 검증

btest `rules/rule-policy`(`killchain_story.pcap`):

- 포트 스캔·SQL 인젝션·랜섬웨어를 끄면 notice·탐지 요약·근거에 0행, 나머지 탐지(웹쉘·Kerberoasting·대용량 유출)는 그대로
- 킬체인 상관은 정찰·피해 단계 없이 나머지 5단계로 이어짐
- 모든 `nsm_sensor.log` 행에 `rule_policy_version`
- 모르는 룰 이름은 시작 경고 후 건너뛰고 나머지는 적용
- 로드 순서 `fixed` → `custom` → `policy`

## 9. 재시작 없는 적용 (검토 결과, 하반기 후보)

Zeek 설정 프레임워크(`option` + `Config::config_files`)로 재시작 없이 바꾸는 방안을 Zeek 9.0.1·8.0.9에서 확인했습니다.

- 목업 룰 정책 화면의 기준값 80개 중 **53개는 가능**(이벤트 처리 중에 읽는 값), **27개는 불가**(집계 구간 16개·집계 임계 11개는 SumStats를 만들 때 굳음).
- `option`도 `redef`가 그대로 되므로 고객 설정과 호환됩니다. 클러스터에서는 매니저가 설정 파일을 읽어 워커로 퍼뜨립니다.
- 설정 파일의 시간 값은 **초 단위 숫자**여야 합니다(`10min`은 10초로 읽힘). 형식이 틀린 값은 **경고 없이 무시**됩니다.

운영하며 재시작 손실(4장)이 문제가 되면, 자주 바꾸는 기준값과 룰 끄기부터 이 방식으로 옮기는 것을 검토합니다.
